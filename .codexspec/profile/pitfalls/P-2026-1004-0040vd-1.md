### P-2026-1004-0040vd-1: Nested worktrees contaminate recursive architecture scans
- claim: When architecture checks report source paths inside nested historical worktrees, verify the same tracked and nonignored feature files in a clean temporary directory before attributing failures to the feature.
- type: pitfall
- scope/when: running repository-wide architecture checks in a checkout containing `.worktrees/` or `.claude/worktrees/`
- root-cause: Architecture tests recursively scan source files beyond Go's selected package list and include old source in nested worktrees, producing legacy-consumer and dependency violations unrelated to the checked-out branch.
- workaround: Preserve the original worktrees; create a temporary `git archive HEAD` verification copy, overlay all tracked and nonignored changed/new files using `git ls-files -co --exclude-standard -z`, and run `go test ./...` there. Recreate the copy or propagate deletions when the target deletes files. Record both the original failure and clean-copy result; do not weaken architecture assertions.
- lesson: A repository scan's filesystem scope can be broader than the build's package scope; verification must identify the exact source tree under test.
- evidence.facts: The original baseline reported legacy symbols in `.worktrees/ask-user-tool/` and duplicated runtime consumers in `.claude/worktrees/`; the unchanged HEAD archive passed `go test ./...`.
